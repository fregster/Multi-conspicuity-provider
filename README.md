# Multi-conspicuity Provider

Docker Compose stack for feeding one Raspberry Pi with multiple RTL-SDR dongles
into several ADS-B and FLARM/OGN aggregator networks, plus a local unified map.

## Architecture

Each frequency gets a single decoder container that owns its SDR and re-publishes
the decoded traffic over the compose network. Every aggregator network then runs
as its own lightweight container that consumes that shared feed - no aggregator's
client software talks to the hardware directly, so dongles are never contended
for and networks can be added/removed independently.

```
 1090MHz SDR --> ultrafeeder (readsb + tar1090 + mlat-hub)
                     |--> local map (tar1090, http://<pi>:8080)
                     |--> adsb.lol, adsb.fi, airplanes.live, planespotters.net,
                     |    ADSB Exchange, theairtraffic.com, adsb.win, HPRadar,
                     |    Fly Italy ADSB, ADSB Italia, Dataero, ADSBiq, PlaneTrack,
                     |    AVDelphi, map.flights, Skydex, FlyOverhead, RealTraffic,
                     |    FlightDeck  (all built into ultrafeeder)
                     |--> Beast Reduce Plus peers, e.g. 1090MHz.uk (BEAST_PEERS, out=)
                     |--> peer-map     (2nd map: ours + peers' in= feeds + peer MLAT, optional)
                     |        ^  |--> mlat-client (our SDR only) --> peer mlat= server
                     |        |  '--> hub: Beast out to peers --+
                     |   hub-gate (host net, UFW, UUID check) <-+-- other stations' out=/in=/mlat=
                     |        '--> mlat-server (peer group MLAT, hub only)
                     |--> piaware      (Beast feed from ultrafeeder)
                     |--> adsbhub      (SBS feed from ultrafeeder)
                     |--> fr24feed     (Beast feed from ultrafeeder)
                     |--> radarbox     (Beast feed from ultrafeeder)
                     |--> planefinder  (Beast feed from ultrafeeder)
                     |--> opensky      (Beast feed from ultrafeeder)

868.8MHz SDR --> ogn-rf --(TCP 50010)--> ogn-decode --> ogn-bridge --> ultrafeeder's SBS input --> tar1090
                                                            |--> aprs.glidernet.org (OGN, when online)
OGN APRS-IS (network-wide, when online) ------------------> ogn-bridge (local SDR wins de-dup)
```

- **ultrafeeder** ([sdr-enthusiasts/docker-adsb-ultrafeeder](https://github.com/sdr-enthusiasts/docker-adsb-ultrafeeder)) decodes 1090MHz ADS-B, serves the tar1090 map, and feeds every network that accepts anonymous Beast/MLAT connections (the list above) directly via its built-in multi-feeder config - none of these need a separate container. Each network gets its own UUID (`*_UUID` in `.env`, generated by `./init-uuids.sh`) so they can't link this station to one another - ultrafeeder would otherwise send one global UUID to all of them - and MLAT runs with `--privacy`, keeping the station off public MLAT sync maps. Standalone `readsb-protobuf` is archived upstream, so this bundled image is the maintained replacement.
- **Beast Reduce Plus peers** are listed in `.env` as `BEAST_PEERS="name,out=host:port,in=host:port;..."` (either endpoint optional; known peers such as 1090MHz.uk are there commented out, with how to register). `peers/peers.sh` wraps the ultrafeeder entrypoint and turns each `out=` into an ultrafeeder feed and each `in=` into an input for **peer-map**, a second SDR-less ultrafeeder serving `/peer-map`. Inbound peer traffic goes only there, never into `ultrafeeder`, so it isn't passed on to the aggregators as if we'd received it. peer-map only runs with `COMPOSE_PROFILES=peer-map`. Every peer is sent `BEAST_PEER_UUID`, which you register with them. An `mlat=host:port` field runs an mlat-client against that peer's MLAT server - inside peer-map, reading our own SDR from `ultrafeeder:30005`, so the results (computed partly from peers' receivers) land only on `/peer-map`; in ultrafeeder, its mlathub would push them into the main readsb. Check with `./peers/test_peers.sh`.
- **Hub** (`COMPOSE_PROFILES=hub`, settings in `.env`): lets other stations running this stack peer with us using `BEAST_PEERS=hub,out=<hub>:30004,in=<hub>:30005,mlat=<hub>:31090`. It adds **mlat-server** ([wiedehopf's fork](https://github.com/wiedehopf/mlat-server) of mutability's server, AGPL-3.0, unmodified image built by [adsb.lol](https://github.com/adsblol/mlat-server)) and **hub-gate** (`hub/gate.py`), which publishes peer-map's Beast input/output and the MLAT server. Remote stations feed us from their main ultrafeeder (own SDR only - readsb puts MLAT results on Beast outputs only with `--forward-mlat`, set only in peer-map, and SBS input never), so nothing loops; but don't point two hubs' `in=` at each other's Beast output. With `HUB_ALLOWED_UUIDS` set, the gate drops Beast/MLAT connections that don't present a listed UUID (Beast Reduce Plus sends it first thing; mlat-client in its handshake). The gate runs on the host network because Docker-published ports bypass UFW; run `./hub/ufw.sh` on the host to open the ports, limited to `HUB_ALLOWED_SOURCES` if set - the only control on the Beast output, since readers send no UUID. Check with `python3 hub/test_gate.py`.
- **piaware** / **adsbhub** / **fr24feed** / **radarbox** / **planefinder** / **opensky** are separate maintained containers for the networks that need their own client software and a per-station key (FlightAware, ADSBHub, FlightRadar24, RadarBox/AirNav Radar, PlaneFinder, OpenSky Network respectively) - they pull Beast/SBS data from `ultrafeeder` over the compose network and have no SDR access themselves.
- **ogn-rf** / **ogn-decode** are custom images (see `ogn/`) built from the official OGN binaries, split the same way: `ogn-rf` owns the 868.8MHz SDR, `ogn-decode` receives its output over TCP and feeds the Open Glider Network APRS server. `ogn-decode` is closed-source freeware (binary-only from glidernet.org); `ogn-rf` is open source but we use the official precompiled binary rather than rebuilding it.
- **ogn-bridge** (see `ogn-bridge/`) gives tar1090 a single unified map with FLARM/OGN traffic alongside ADS-B, and works with **no internet** (e.g. an airfield with only the local SDR). `ogn-decode` is configured to use `ogn-bridge:14580` as its APRS server; the bridge speaks just enough APRS-IS to accept it, turns each position into a synthetic SBS contact (using the `~`-prefixed non-ICAO-address convention `readsb` already supports) for `ultrafeeder`'s SBS input port, and relays every line on to `aprs.glidernet.org` whenever that is reachable (lines are dropped, not queued, while offline - the OGN network wants live data). When online it also subscribes to OGN's public APRS-IS feed with a range filter around the station, so aircraft our dongle can't hear still appear. **De-dup:** the local SDR is treated as the more recent/reliable source - once an aircraft has been heard locally, network reports for the same address are ignored for 30s (`LOCAL_HOLD_S`), so the icon never flips between the two. Trade-off: `ogn-bridge` sits in the path of the OGN upload, so if it is down `ogn-decode` cannot reach the network (it reconnects when the bridge returns). Check with `python3 ogn-bridge/test_bridge.py`.
- **traefik** is a reverse proxy for external HTTPS access, e.g. via a router port-forward to `80`/`443`. It's configured with no certificate resolver, so it falls back to its own auto-generated self-signed certificate - browsers will show a one-time trust warning, but no domain or ACME/DNS setup is required. Every service with a web UI is exposed under a path prefix with its own Traefik `stripprefix` middleware:
  - `/tar1090` - the map (ultrafeeder)
  - `/piaware` - PiAware status page / skyaware
  - `/fr24feed` - FlightRadar24 feed status
  - `/planefinder` - PlaneFinder feed status
  - `/ogn-rf`, `/ogn-decode` - FLARM/OGN decoder status pages

  The landing page also shows live health, refreshed every 15s from `/status.json` (served by the **status** container, see `status/status.py`): every container's state and Docker healthcheck; each ultrafeeder aggregator's Beast connection and MLAT sync (from ultrafeeder's `/metrics` and `/mlat-client-stats/`); the dedicated feeders' health (their own healthchecks check their uplink); whether adsb.fi and airplanes.live actually see our Beast/MLAT feeds (their public per-IP APIs, cached 5 min); and the OGN links reported by `ogn-bridge` (local receiver, local OGN → tar1090, OGN network → tar1090, upload to glidernet). `status` reads the container list through the same read-only `socket-proxy` as Traefik and passes on only name/state/status.

  This works because all of these apps reference their own assets with relative paths - verify that's true before adding another one this way (or use `Host()` rules instead if an app uses root-absolute asset paths). ADSBHub and RadarBox/AirNav Radar have no web UI, so they aren't in the list. The site root (`/`) serves a static holding page (`landing/`, plain nginx) linking to each of these - it's a Traefik catch-all with an explicit low priority so it never shadows the more specific per-service routers. tar1090 also stays reachable directly over plain HTTP on `TAR1090_PORT` (e.g. for LAN use without the cert warning), same as `ogn-rf`/`ogn-decode` on their own `OGN_RF_STATUS_PORT`/`OGN_DECODE_STATUS_PORT`. Note Traefik's Docker provider won't route to a container until its own healthcheck passes, so a freshly (re)started service can 404 through the proxy for a minute or two even though it's actually coming up fine.

### Self-recovery

- Docker's `restart: unless-stopped` only restarts a container whose process exits; a container whose healthcheck says `unhealthy` (e.g. fr24feed after losing its uplink) is left alone. **healer** (`healer/healer.py`) restarts those, opted in with an `autoheal` label: `autoheal=local` for ultrafeeder (its healthcheck is purely local, so it is always restarted) and `autoheal=uplink` for the dedicated feeders, which are only restarted while the internet is reachable - offline they all go unhealthy and a restart can't help. Each container is restarted at most once per 30 min. Restarts go through a second socket-proxy (`socket-proxy-restart`) that allows nothing but container stop/restart/kill; listing stays on the read-only one.
- On the host, `systemd/install.sh` also installs **net-watchdog.timer**: if eth0 has no default route or its gateway stops answering pings for 5 minutes, it re-activates the interface with `nmcli` to force a fresh DHCP lease; if that fails twice it bounces the link, and after 30 minutes it reboots - but only if the gateway answered earlier that boot, so a site with no LAN never reboot-loops. It also makes the journal persistent (Raspberry Pi OS keeps it in RAM, losing every log across a reboot) and turns off Energy-Efficient Ethernet on eth0, the suspected cause of the Pi 5 NIC silently stopping passing traffic.
- The dedicated feeders are capped at 15% of a CPU core (`x-feeder` in `docker-compose.yml`) so a misbehaving client can't starve readsb or ogn-decode, whose decoding and MLAT timing depend on it.
- SD-card wear: readsb writes its state only on shutdown (`READSB_WRITE_STATE_ONLY_ON_EXIT`), graphs1090 flushes to disk daily (`GRAPHS1090_REDUCE_IO`), and ultrafeeder's `/var/log` is tmpfs.

## Prerequisites

- One RTL-SDR per frequency you want to receive (1090MHz for ADS-B, 868.8MHz for FLARM/OGN). A single dongle can run ADS-B-only until a second is added.
- Docker + Docker Compose on the host (a Raspberry Pi 5 running Debian is the reference target).

## Checks

`./check.sh` runs every code-standard and test gate, and CI runs the same script. Everything is discovered from the repo:
- shellcheck on every `*.sh`, and ruff (pinned in CI) on every Python file;
- every image is built; each service's `test_*.py` runs inside its image, and every other `test_*.sh` / `test_*.py` runs on the host;
- every Python directory needs its own `ruff.toml` and a `test_*.py`;
- any file type with no checker fails until one is added, or until it's listed in `check.sh` as needing none.

CI also runs hadolint on every Dockerfile, actionlint, `docker compose config` and gitleaks.

## Setup

1. `cp .env.example .env`, fill in your station's coordinates and each network's API key, then run `./init-uuids.sh` to generate the per-aggregator UUIDs (Compose refuses to start while any is blank). Register `ADSBLOL_UUID` at https://adsb.lol/claim if you want adsb.lol stats.
2. Running locally on the host itself: `docker compose up -d --build`.
3. Deploying to a remote host over SSH (e.g. the Pi): also fill in `PI_HOST`/`PI_USER` in `.env` (used only by `deploy.sh`, not read by Compose itself), then run `./deploy.sh` - it rsyncs the repo over and runs `docker compose up -d --build` there.
4. Starting on boot: on the host running the stack, run `./systemd/install.sh` once. It installs and enables a `multi-conspicuity-provider.service` unit, manageable the normal way: `sudo systemctl {start,stop,restart,status} multi-conspicuity-provider`. It also installs the `net-watchdog.timer` uplink watchdog (see Self-recovery). If the kernel's DVB-T drivers (`dvb_usb_rtl28xxu` etc.) aren't blacklisted, it offers to add `/etc/modprobe.d/blacklist-rtlsdr.conf` - otherwise they can claim the SDRs at boot and readsb/ogn-rf fail with `usb_claim_interface error -6`.

## Offline map (optional)

tar1090's basemap normally comes from the internet, so at a site with no connection the aircraft sit on a blank map. `tiles/offline_tiles.py` (stdlib Python, run on the host) fills `OFFLINE_TILES_DIR` (default `/usr/local/share/osm_tiles_offline`, outside the repo so `deploy.sh`'s rsync never deletes it) with a global basemap plus extra detail in a bounding box:

```
sudo python3 tiles/offline_tiles.py --bbox <west>,<south>,<east>,<north>   # e.g. --bbox -2.0,51.0,0.0,52.0
docker compose restart ultrafeeder
```

then pick "OpenStreetMap offline" in the map's layer menu. Defaults: the whole world to zoom 6, the box to zoom 10, both from wiedehopf's prebuilt 2022 OSM tile packs (~2GB download, streamed - only kept tiles are written, a few hundred MB for a county-sized box). More detail needs `--bbox-zoom N --tile-url 'https://.../{z}/{x}/{y}.png'` pointing at a raster provider whose terms allow offline/bulk downloads; tile.openstreetmap.org forbids that and is refused. Re-running adds tiles; delete the directory to start over. Check with `python3 tiles/test_offline_tiles.py`.

## Host hardening (optional)

`./harden-host.sh` clones [dockerHosting](https://github.com/DigitalisCloudServices/dockerHosting) to `/opt/dockerHosting` and runs its `setup.sh` baseline (ufw, SSH/fail2ban, kernel sysctls, chrony, unattended-upgrades, auditd, AppArmor, Docker daemon log limits). Run it on the host itself - it's interactive and disables SSH password login, so confirm key access first. It is tuned for this stack:

- Skips dockerHosting's own Traefik (this stack runs one) and AIDE (heavy SD-card wear) - override with `HARDEN_SKIP=traefik` on SSD/NVMe.
- Skips USB-storage blacklisting automatically when `/` is on a USB drive.
- Passes `--userns-remap=no`: remapped container root can't open `/dev/bus/usb`, so the SDRs would disappear.

Pin a dockerHosting branch or tag with `DOCKERHOSTING_REF`. Extra arguments go straight to `setup.sh`, e.g. `./harden-host.sh --report` for a read-only posture audit.

## Adding a second SDR

Find each dongle's serial with `rtl_eeprom -d 0` (repeat with `-d 1`, etc.) - stop whichever service currently holds a dongle first (`usb_claim_interface error` means something already has it open). Factory dongles usually all share the same default serial (`00000001`), so set a unique one per dongle with `rtl_eeprom -d <index> -s <serial>` if needed - use a non-numeric serial (e.g. `SDR1090`), since readsb treats a purely-numeric device string as an index rather than a serial. Then set `SDR_1090_SERIAL` and `SDR_FLARM_SERIAL` in `.env` so each service always binds the same physical dongle regardless of USB enumeration order.

## Adding another aggregator network

- If it accepts generic Beast/MLAT feeds (like airplanes.live, ADSB.fi, ADSB Exchange), add its `adsb,...` (and `mlat,...,--privacy`) entries to `ULTRAFEEDER_CONFIG` in `docker-compose.yml` with `uuid=${NAME_UUID:?}`, and a blank `NAME_UUID=` to `.env.example` - see the [Ultrafeeder README](https://github.com/sdr-enthusiasts/docker-adsb-ultrafeeder#all-in-one-configuration-using-ultrafeeder_config) for the aggregator list and connection strings.
- If it needs its own client software (like PiAware/ADSBHub), add a new service pointed at `ultrafeeder`'s Beast (`30005`) or SBS (`30003`) port, following the `piaware`/`adsbhub` services as a template.
